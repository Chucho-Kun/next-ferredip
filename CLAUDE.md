@AGENTS.md

## Project overview

Ferredip is an e-commerce storefront for tools/hardware (multiple brands and categories), built with Next.js (App Router) + React + TypeScript. It uses PostgreSQL (hosted on Railway) via Drizzle ORM, Mercado Pago for checkout, Zustand for client state, and Resend/Nodemailer for transactional email. Deployed on Railway.

## Commands

- `npm run dev` — start the dev server (Turbopack). `npm run dev:webpack` is the same command using the classic webpack dev server.
- `npm run build` — production build.
- `npm run start` — run the production build.
- `npm run lint` — ESLint (flat config, `eslint-config-next` core-web-vitals + typescript).
- `npm run db:studio` — open Drizzle Studio against `DATABASE_URL`.
- `npm run import:csv` — runs `scripts/import-csv.ts` to bulk-insert `productos.csv` into the `productos_` table. The script's own header comment says it currently doesn't work reliably; importing via TablePlus (or another Postgres client) directly is the recommended path instead.
- There is no `test` script and no Jest/Playwright config file, even though `jest`, `@testing-library/*`, and `@playwright/test` are installed as devDependencies — a test runner is not wired up yet.

Drizzle migrations live in `drizzle/` (SQL files + `meta/`), generated from the schema in `src/shared/db/schema` per `drizzle.config.ts`. Use `drizzle-kit` (via `npx drizzle-kit generate` / `push`) when changing the schema — there's no npm script for it currently.

## Environment

Configuration is read from `.env` (see `drizzle.config.ts` and `src/shared/db/index.ts`). Expected variables: `DATABASE_URL`, `NEXT_PUBLIC_URL`, `NEXT_PUBLIC_GTM_ID`, `NEXT_PUBLIC_MERCADOPAGO_PUBLIC_KEY`, `MERCADOPAGO_ACCESS_TOKEN`, `RESEND_API_KEY`, `EMAIL_USER`, `EMAIL_PASSWORD`, `EMAIL_APP_PASSWORD`.

## Architecture

### Path alias

`tsconfig.json` maps `@/*` to the **repo root**, not `src/`. Imports look like `@/src/shared/db`, `@/src/store/cartStore`, etc. — don't assume the common `@/` = `src/` convention from other Next.js projects.

### Route groups (`app/`)

- `app/(public)` — the storefront: home, `producto/[id]/[slug]`, `categoria/[slug]`, `marca/[slug]`, `marcas`, `productos` (category overview grid), `resultados/[slug]` (search results), `carrito-de-compra`, `compra` (checkout + `pago-exitoso`/`pago-fallido`/`pago-pendiente` result pages), plus static pages (`contacto`, `soy-mayorista`, `terminos-y-condiciones`, `aviso-de-privacidad`).
- `app/(admin)` — admin panel (currently only `productos/relacionados`, for managing related-product associations). There is no `middleware.ts` and no auth check found in the admin layout/routes — treat admin pages/APIs as currently unprotected rather than assuming they're gated.
- `app/api` — route handlers: `admin/productos` (list/manage products, including `[id]/relacionados`), `mercadopago/preference` and `mercadopago/process-payment` (checkout flow), `search`, `send-email`.
- `app/sitemap.ts`, `app/feed.xml/route.ts`, `app/products.xml/route.ts` — generated SEO/feed endpoints.

### Data layer (`src/shared/db`)

- `index.ts` — single `pg.Pool` + `drizzle()` instance shared app-wide (SSL only in production).
- `schema/productList.ts` — the whole catalog lives in one table, `productos_` (Drizzle table `productos`). There's no separate brands/categories table: `marca` and `categoria` are free-text varchar columns, and product variants are encoded by splitting `descripcion` on `|` (see `getProductsByGroupsofTrademarks`/`getProductsByGroupsofCategories` in `queries.ts`). Sort order is driven by the `orden_prod`/`orden_cat` integer columns, not by insertion order or price.
- `queries.ts` — all product read queries, plus `slugToMarca`/`slugToCategory` helpers that map URL slugs to display names via a hardcoded lookup table (extend these maps when adding a new brand/category slug). Catalog queries hide products whose `precio` is empty or `0` via the shared `precioMayorACero` filter (`gt(sql\`${productos.precio}::numeric\`, 0)`, combined with `and(...)`; the `::numeric` cast is required because `precio` is a `varchar`). It's applied in `getProductsByGroupsofTrademarks`, `getProductsByGroupsofCategories`, `getRecomendedProducts`, `getAllProductosXML`, `getRelatedProducts`, and separately (inlined, not imported) in `app/api/search/route.ts`'s `GET` handler — add it to any new catalog query too. `getProductById` deliberately skips it, since a product page resolves by direct URL regardless of price.
- `marcas.ts`, `resultados.ts`, `contact-info.ts` are **not** query modules despite living alongside `queries.ts`: `marcas.ts` is a static array of brand logos (`/marcas/*.webp`, with commented-out entries awaiting artwork, same pattern as `db/productos.ts`), `resultados.ts` only holds shared TypeScript types (`ResultadosType`, `RelatedProductType`, `VariantOptionType`), and `contact-info.ts` exports the `whatsAppNumber` constant (see Misc below).
- `productos.ts` — not a DB query module despite living in `db/`: it's a static array mapping category slugs to their `/productos/*.webp` image, used by the home page and `app/(public)/productos` to render the category grid. Commented-out entries are categories awaiting artwork — uncomment once the image exists in `public/productos/`.

### State & actions

- `src/store` — Zustand stores: `cartStore.ts` (cart contents, persisted to `localStorage` under key `ferredip-cart`, computes subtotal/shipping/total — free shipping threshold is $5000) and `deliveryStore.ts`.
- `src/actions` — server actions. `contact.ts` (`sendContactEmail`, backed by `app/api/send-email`) still exists, but the `/contacto` form (`ContactoCliente.tsx`) no longer calls it — its submit handler now opens WhatsApp with a pre-filled message instead, leaving the `sendContactEmail` import unused.
- `src/utils` — `formatPrice.ts`, `slugify.ts` (URL slug generation for products/brands/categories), `gtm.ts` (Google Tag Manager event pushes), `orderSnapshot.ts`.
- `src/hooks` — `useDeleteToast.tsx`.

### Components (`src/shared/components`)

Flat-ish by domain rather than by route: top-level components are storefront sections (product cards/lists, brand/category results, sliders), with subfolders for `cart/` (checkout UI incl. `MercadoPagoBrick`/`MercadoPagoButton`), `dashboard/` (admin related-products dashboard, with its own `types/producto.ts`), `header/`, `footer/`, and `analytics/` (`ViewItemListTracker.tsx`, fires GTM view-item-list events).

- **Búsqueda por id de producto (2026-08-17, en español, spec `specs/02-busqueda-por-id-producto.md`):** el buscador del header (`SearchBar.tsx` + `app/api/search/route.ts`) sólo consultaba `clave`, `descripcion` y `marca` — no el `id` (el identificador que aparece en la URL del producto, en los correos y en el nombre de archivo de la foto). - **Evaluación de migrar fotos a un CDN (2026-08-20, en español):** con el commit de fotos adicionales de arriba, `public/fotos/` pasó de ~576 MB a rondar **~2 GB** (sumando los 1.5 GB nuevos de `public/fotos/adicionales/`), y el `.git` creció en la misma medida. El usuario preguntó si esto podía generar problemas de rendimiento o costo en Railway (plan Hobby) con ~1000–3000 visitas/mes; se investigó (`WebSearch` sobre `docs.railway.com/pricing/plans`, `bunny.net/pricing`, `developers.cloudflare.com/r2/pricing`) y la conclusión fue: **el tráfico de ese volumen no es un problema de costo** — Railway cobra CPU/RAM por uso real (no por peso del repo) y el egress sale $0.05/GB, así que aun con uso intensivo del zoom el costo mensual sería de centavos. El riesgo real es de **build/deploy**: el plan Hobby trae 500 minutos de build/mes y del orden de 5GB de almacenamiento por servicio, y cada deploy copia los ~2GB de `public/fotos/` a la imagen — eso alarga los builds y come minutos más rápido a medida que crece el catálogo, además de hacer más lento el clon del repo (en esta misma sesión, `git add`/`git commit`/`next build`/`next dev` tardaron varios minutos cada uno por el filesystem local — no es Railway, pero es el mismo síntoma de "repo pesado"). Se comparó **Cloudflare R2** (recomendado: egress gratis siempre, free tier de 10GB de storage que cubre el peso actual completo, API compatible con S3 así que se integraría con un script parecido a `download-truper-images.mjs`, y CDN de Cloudflare incluido gratis al conectar un dominio propio) contra **Bunny.net** (CDN aún más barato, $0.005/GB, y storage a $0.01/GB con mínimo de $1/mes, pero sin free tier de almacenamiento y con API propia en vez de S3-compatible). Punto importante para cuando se implemente: un CDN como proxy/pull-zone delante de Railway solo cachea tráfico, no achica `public/fotos/` ni el `.git` — para resolver el problema de peso del repo las fotos tienen que moverse físicamente a R2/Bunny y servirse desde ahí. No se implementó nada de esto todavía; queda como candidato a spec futuro (algo como `06-migracion-fotos-a-cdn`).
- **Memory leak por combinatoria del optimizador de imágenes (2026-08-24, en español):** Railway reportó memoria del servicio `next-ferredip` subiendo en "escalera" de ~500MB a >1.5GB en 6 horas sin bajar nunca, coincidiendo con ráfagas de crawl de Googlebot. No es un leak de heap de JS: `node_modules/next/dist/server/image-optimizer.js` (Next 16.2.6) invoca `sharp` sin ningún límite de operaciones concurrentes entre requests distintos (solo auto-reduce threads *dentro* de una misma operación) — cada request a `/_next/image` con cache-miss decodifica/recodifica en memoria la foto grande (1800×1800) del producto. El catálogo (~2170 productos × hasta 4 fotos) combinado con `deviceSizes`×`imageSizes`×`qualities`×`formats` de `next.config.ts` generaba una matriz enorme de variantes nunca antes pedidas, así que un crawl agresivo garantizaba muchos cache-misses concurrentes — y la memoria nativa de sharp/libvips no se devuelve completamente al SO entre ráfagas (fragmentación de malloc de glibc en contenedores Linux, problema conocido de sharp/libvips), de ahí que la gráfica nunca bajara. El `cacheMaxMemorySize: 0` / `cacheHandler: undefined` que ya estaba en `next.config.ts` (comentado como "solución temporal para el LRUCache") es del Data/ISR Cache de Next, no del optimizador de imágenes — no mitigaba nada de esto. Mitigación aplicada en `next.config.ts`: `images.formats` a solo `['image/webp']` (se quitó AVIF, el códec más caro de recodificar en sharp), `images.qualities` a un solo valor `[75]` (antes `[75, 85]` — se ajustó también `quality={85}` → `{75}` en `ProductImageZoom.tsx`, único lugar que pasaba `quality` explícito), `images.minimumCacheTTL` a 2592000 (30 días, ya que las fotos de producto no cambian sin un deploy nuevo) para que un re-crawl reutilice la variante ya generada en disco en vez de volver a invocar sharp, y `experimental.imgOptConcurrency: 1` para acotar explícitamente los threads nativos que sharp usa por operación en el contenedor de Railway. Pendiente de evaluar si la memoria sigue creciendo tras el deploy: (a) variable de entorno `MALLOC_ARENA_MAX=2` en Railway (mitigación estándar para fragmentación de malloc de glibc con addons nativos como sharp, no es un cambio de este repo), (b) pre-generar una versión intermedia (~800×800) de las fotos para que la galería/tarjetas no fuercen a sharp a decodificar el original de 1800×1800 solo para miniaturas de 72–384px (el `<img>` del zoom en `ProductImageZoom.tsx` sí necesita el original de 1800×1800 y no pasa por el optimizador, así que no se toca), (c) límite de memoria/restart policy del servicio en Railway como red de seguridad.

Metadata de `/productos`: `alternates.canonical` pasó de `'/productos'` a `` `https://ferredip.com.mx/categoria/${primeraCategoria}` `` (absoluto — evita el duplicado sin redirigir con 301, porque el link del header seguiría apuntando de hecho a una categoría concreta), y `keywords` pasó de la lista hardcodeada de la era Dipemsa (`tablaroca`, `cempanel`, `plafones`…) a `productos.map(({ name }) => slugToCategory(name))`. `/productos` **sigue en `app/sitemap.ts`** aunque declare un canonical distinto (inconsistencia menor y consciente; sacarla queda para otro spec). **Hallazgo no previsto por el spec:** `slugToMarca`/`slugToCategory` vivían en `src/shared/db/queries.ts`, que hace `import { db } from '@/src/shared/db'` (arrastra el driver `pg`); importarlas desde un `'use client'` rompía `npm run build` (`Module not found: Can't resolve 'util/types'` vía `pg/lib/utils.js`). Se movieron verbatim a `src/shared/db/slugs.ts` (sin dependencia de BD) y `queries.ts` las reexporta (`import { slugToMarca, slugToCategory } from './slugs'; export { slugToMarca, slugToCategory };`) — los ~6 importadores existentes no se tocaron; los componentes cliente deben importar de `./slugs`. **Otro efecto del cambio (no resuelto, anotado):** `/productos` pasó de estática-sin-datos a estática **con una query a la BD en build time** (`getProductsByGroupsofCategories`), así que sus fichas quedan congeladas hasta el próximo deploy y el build depende de que `DATABASE_URL` sea alcanzable; `/categoria/[slug]` sigue siendo dinámica. Si se quiere que refleje cambios de catálogo sin redeploy, agregarle `export const dynamic = 'force-dynamic'` o `revalidate` — fuera del alcance de este spec. Fuera de alcance (specs futuros): el mismo menú en `/marca/[slug]` (`TrademarckResults.tsx`), menú de marcas, filtros combinados (categoría+marca, precio, orden), paginación/scroll infinito, contador de productos por categoría, y unificar la fuente del menú (`productos.ts` refleja qué categorías tienen imagen, no cuáles tienen catálogo con precio).
